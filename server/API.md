# HMS Backend API Documentation

This document catalogs every HTTP endpoint currently exposed by `server/src`. It is a read-only reference generated by inspecting the routes, controllers, services, and validation schemas — no backend code was changed to produce it.

## Base URL

```
http://localhost:5000/api/v1
```

(`PORT` and other runtime config come from `server/.env`; the prefix `/api/v1` is mounted in `server/src/config/Routes.ts`.)

## Response envelope

Every endpoint responds via `apiResponse` (`server/src/utils/apiResponse.ts`):

```json
// success
{ "success": true, "message": "...", "data": <payload> }

// error
{ "success": false, "message": "...", "errors": null }
```

## Auth

- Bearer JWT in `Authorization: Bearer <token>`, issued by `POST /auth/login`.
- `authMiddleware` (`server/src/middleware/authMiddleware.ts`) verifies the token, loads the user from `UserModel`, and attaches it to `req.user`. Missing/invalid token → `401`.
- `restrictMiddleware('role1', 'role2', ...)` (`server/src/middleware/restrictMiddleware.ts`) checks `req.user.role` against an allow-list. Must run after `authMiddleware`. Mismatch → `403`.

## Roles (`server/src/models/UserModel.ts`)

```
superadmin | admin | doctor | nurse | receptionist | patient
```

## Multi-tenancy note (`hospitalId`)

`UserModel.hospitalId` (ref: `Hospital`, default `null`) scopes every non-superadmin account to one hospital:

- `POST /hospitals` creates a hospital **and** its admin account in one call, explicitly setting the new admin's `hospitalId` to the new hospital's `_id` (see `hospitalService.ts::createHospital`, which calls the same `registerUser` service that backs `POST /auth/register`).
- `POST /auth/register` reads `req.user.hospitalId` (the currently authenticated caller — an admin or receptionist) and copies it onto the new doctor/nurse/receptionist/patient it creates. If the caller's own `hospitalId` is `null` (e.g. a superadmin, or an admin that itself predates this flow), the new account also gets `null` — there is no other source for this value.
- `GET /auth/doctors`, `/auth/nurses`, `/auth/receptionists`, `/auth/patients` all filter `{ hospitalId: req.user.hospitalId }`, so an admin/receptionist only ever sees accounts scoped to their own hospital.

## 1. Auth & User Directory — `/api/v1/auth` (`authRoute.ts`)

### POST `/auth/register`
Create a doctor, nurse, receptionist, or patient account.

- **Auth:** required (`authMiddleware`). Any authenticated role may call it (no `restrictMiddleware`), but see the `hospitalId` note above — realistically this is called by an authenticated `admin` or `receptionist`.
- **Validation:** `userSchema` (`validations/userValidation.ts`), a single schema for all four roles with role-conditional required fields via `.superRefine`:

  | Field | Type | Required for |
  |---|---|---|
  | `firstName`, `lastName` | string (2–50) | all |
  | `email` | email | all |
  | `phone` | string (7–20) | all |
  | `role` | `'doctor' \| 'nurse' \| 'receptionist' \| 'patient'` | all (note: `admin`/`superadmin` are deliberately excluded — see below) |
  | `department` | string (Department name or ObjectId) | doctor, nurse, patient |
  | `specialty` | string (Specialty name or ObjectId) | doctor |
  | `licenseNumber` | string | doctor, nurse |
  | `qualification` | string | doctor |
  | `experience` | number ≥ 0 | doctor |
  | `shiftStart`, `shiftEnd` | string | doctor, nurse, receptionist |
  | `staffDepartment` | string (free text, e.g. "Front Desk") | receptionist |
  | `ward` | string (free text, e.g. "ICU") | nurse |
  | `gender` | `'male' \| 'female'` | patient |
  | `patientStatus` | `'stable' \| 'observation' \| 'critical' \| 'discharged'` | patient |
  | `doctor` | string (attending doctor's `userId`, email, or ObjectId) | patient |
  | `admissionDate` | coercible date | patient |
  | `age` | number 0–150 | patient |
  | `bloodGroup` | `A+ \| A- \| B+ \| B- \| AB+ \| AB- \| O+ \| O-` | patient |
  | `password` | string ≥ 6 | never used — see below |

- **Behavior** (`authService.ts::registerUser`):
  - Rejects if `email` already exists (`409`).
  - `department`/`specialty` may be sent as a human-readable name (case-insensitive exact match against `DepartmentModel`/`SpecialtyModel`) or an ObjectId string — resolved via `resolveReference`.
  - `doctor` (patient's attending physician) may be sent as a `userId` (e.g. `D-12345`), an email, or an ObjectId — resolved via `resolveDoctorId`, scoped to `role: doctor`.
  - The client-supplied `password` is **ignored**. A random 8-character password is always generated, hashed, and emailed to the new user (`WelcomeEmail` template via `sendEmail`), along with a login URL (`${FRONTEND_URL}/login`).
  - A human-readable `userId` is generated via `generateStaffId(role)`: prefix `D-` doctor, `N-` nurse, `R-` receptionist, `P-` patient, `+5 random digits`.
  - `hospitalId` is copied from the caller (`req.user.hospitalId`) — see the multi-tenancy note above.
- **Response:** `201`, `{ user: <sanitized user> }` (role-scoped fields only — see `sanitizeUser.ts`).
- **Related APIs:**
  - `POST /auth/login` — the credentials this creates are for; the emailed password is only usable there.
  - `GET /auth/doctors` — the `doctor` field on a patient must resolve to an account created here with `role: doctor`.
  - `GET /departments`, `GET /specialties` — the values accepted for `department`/`specialty` come from these lists.
  - `POST /hospitals` — uses the exact same underlying `registerUser` service to create a hospital's first `admin` account (the one path that *can* create a privileged role, and the only place `hospitalId` originates from something other than the caller).

### POST `/auth/login`
- **Auth:** none.
- **Validation:** `loginSchema` — `email`, `password` (≥ 6 chars).
- **Behavior:** verifies password hash, issues `{ token, refreshToken }` (`loginAccessToken`/`loginRefreshToken`, `utils/jwt.ts`).
- **Response:** `200`, `{ token, refreshToken, user: <sanitized user> }`.
- **Related APIs:** `POST /auth/register` (issues the account this logs into), `GET /auth/me` (typically called immediately after, using the returned token).

### GET `/auth/me`
- **Auth:** required, any role.
- **Response:** `200`, sanitized `req.user`.
- **Related APIs:** `POST /auth/login` (source of the token used here).

### GET `/auth/doctors`
List doctors in the caller's hospital, optionally filtered by department. Built primarily to populate "select a doctor" dropdowns.
- **Auth:** required, `restrictMiddleware('admin', 'receptionist')`.
- **Query:** `?department=<DepartmentId>` (optional).
- **Response:** `200`, array of **`{ _id, firstName, lastName, userId }` only** — note this is a narrower projection than `/nurses`, `/receptionists`, `/patients` below (no email/phone/department/shift/etc.).
- **Related APIs:** `POST /auth/register` (`role: doctor`) creates the records this lists; `POST /auth/register` (`role: patient`) consumes a doctor's `userId`/email as its `doctor` field.

### GET `/auth/nurses`
- **Auth:** required, `restrictMiddleware('admin', 'receptionist')`.
- **Response:** `200`, full nurse documents for the caller's hospital (no field projection) — includes `department` (ObjectId), `ward`, `licenseNumber`, `shiftStart`/`shiftEnd`, `dutyStatus`, etc.
- **Related APIs:** `POST /auth/register` (`role: nurse`) creates these records.

### GET `/auth/receptionists`
- **Auth:** required, `restrictMiddleware('admin', 'receptionist')`.
- **Response:** `200`, full receptionist documents — includes `staffDepartment`, `shiftStart`/`shiftEnd`, `dutyStatus`, etc.
- **Related APIs:** `POST /auth/register` (`role: receptionist`) creates these records.

### GET `/auth/patients`
- **Auth:** required, `restrictMiddleware('admin', 'receptionist')`.
- **Response:** `200`, full patient documents — includes `department` (ObjectId), `doctor` (ObjectId), `gender`, `patientStatus`, `age`, `bloodGroup`, `admissionDate`, etc.
- **Related APIs:** `POST /auth/register` (`role: patient`) creates these records; `GET /auth/doctors` resolves the `doctor` ObjectId to a display name.

### PATCH `/auth/duty-status`
Clock in/out.
- **Auth:** required, `restrictMiddleware('doctor', 'nurse', 'receptionist')`.
- **Validation:** `updateDutyStatusSchema` — `dutyStatus: 'On Duty' | 'Off Duty'`.
- **Behavior:** going `Off Duty` clears `availabilityStatus`; coming `On Duty` with no `availabilityStatus` set defaults it to `Available`.
- **Response:** `200`, sanitized updated user.
- **Related APIs:** `PATCH /auth/availability-status` (depends on this being `On Duty` first); the resulting `dutyStatus` is what `GET /auth/nurses`/`GET /auth/receptionists` report back.

### PATCH `/auth/availability-status`
- **Auth:** required, `restrictMiddleware('doctor', 'nurse', 'receptionist')`.
- **Validation:** `updateAvailabilityStatusSchema` — `availabilityStatus: 'Available' | 'Break' | 'Busy'`.
- **Behavior:** `400` if the user is currently `Off Duty` ("Go on duty first").
- **Response:** `200`, sanitized updated user.
- **Related APIs:** `PATCH /auth/duty-status` (prerequisite).

## 2. Departments — `/api/v1/departments` (`departmentRoute.ts`)

### GET `/departments`
- **Auth:** none (public).
- **Response:** `200`, array of all departments.
- **Related APIs:** consumed by `POST /auth/register`'s `department` field (by name or id) and by `GET /auth/doctors`/`nurses`/`patients` for resolving department names on the client.

### GET `/departments/:id`
- **Auth:** none (public).
- **Response:** `200`, single department or `404`.

### POST `/departments`
- **Auth:** required, `restrictMiddleware('admin', 'superadmin')`.
- **Validation:** `createDepartmentSchema` — `name` (2–50), `description` (optional, ≤500), `isActive` (optional).
- **Response:** `201`, created department.
- **Related APIs:** new departments become valid values for `POST /auth/register`'s `department`/role-specific fields.

### PATCH `/departments/:id`
- **Auth:** required, `restrictMiddleware('admin', 'superadmin')`.
- **Validation:** `updateDepartmentSchema` (all fields from create, optional).
- **Response:** `200`, updated department.

### DELETE `/departments/:id`
- **Auth:** required, `restrictMiddleware('admin', 'superadmin')`.
- **Response:** `200`, `data: null`.
- **Caution:** existing users referencing this department by ObjectId are not cascaded/checked.

Identical shape to Departments, scoped to doctor specialties.

### GET `/specialties` — public, list all.
### GET `/specialties/:id` — public, single specialty.
### POST `/specialties` — `restrictMiddleware('admin', 'superadmin')`; `createSpecialtySchema` (`name` 2–100, `description` optional ≤500, `isActive` optional).
### PATCH `/specialties/:id` — `restrictMiddleware('admin', 'superadmin')`; partial schema.
### DELETE `/specialties/:id` — `restrictMiddleware('admin', 'superadmin')`.

**Related APIs:** consumed by `POST /auth/register`'s `specialty` field (doctor role only, by name or id).

## 4. Hospitals — `/api/v1` (`hospitalRoute.ts`)

Note the inconsistent base path — these routes are mounted at the bare `/api/v1` prefix (not `/api/v1/hospitals`), and each route itself supplies the `/hospitals` (or `/get-hospitals`) segment.

### POST `/api/v1/hospitals`
Creates a hospital **and** its first admin account together.
- **Auth:** required (`authMiddleware` only — no role restriction currently enforced here, despite this being the endpoint that provisions a new tenant + privileged `admin` account).
- **Validation:** `hospitalSchema` — `hospitalName`, `hospitalCode`, `hospitalEmail` (email), `hospitalPhone`, `address: { addressLine1?, addressLine2?, city, state?, country, postalCode? }`, `admin: { firstName, lastName, email, phone? }`.
- **Behavior:** rejects duplicate `hospitalEmail` (`409`); creates the hospital with `status: 'trial'` and a 30-day `trialEndsAt`; then calls `registerUser` (the same service behind `POST /auth/register`) with `role: admin` and `hospitalId` set to the new hospital — this is the only path that can create an `admin` account, since `POST /auth/register`'s schema explicitly excludes `admin`/`superadmin`. If admin creation fails, the hospital is rolled back (deleted).
- **Response:** `201`, `{ hospital, admin: <sanitized admin user> }`.
- **Related APIs:** `POST /auth/register` (shared `registerUser` logic); every subsequent `POST /auth/register` call made by this new admin inherits its `hospitalId`.

### GET `/api/v1/get-hospitals`
- **Auth:** required, `restrictMiddleware('superadmin')`.
- **Query:** `?page=1&limit=10`.
- **Response:** `200`, `{ hospitals: [...with totalUser & admin...], pagination: { page, limit, total, totalPages } }`. Each hospital is enriched with a live count of `doctor`/`nurse`/`receptionist`/`patient` users and its `admin` user (via `UserModel.find`/`findOne` on `hospitalId`).
- **Related APIs:** the `totalUser` count reflects everything created via `POST /auth/register` under that hospital.

### GET `/api/v1/hospitals/:id`
- **Auth:** required, `restrictMiddleware('superadmin')`.
- **Response:** `200`, single hospital or `404`.

### PATCH `/api/v1/hospitals/:id`
- **Auth:** required, `restrictMiddleware('superadmin')`.
- **Body:** any hospital fields, plus an optional `admin: {...}` object to update the hospital's admin user in the same call (`findOneAndUpdate({ hospitalId, role: admin })`).
- **Response:** `200`, `{ hospital, admin }`.
- **Note:** unlike the other routes, this controller has no `validateSchemaPayload` — the body is not schema-validated before use.

### DELETE `/api/v1/hospitals/:id`
- **Auth:** required, `restrictMiddleware('superadmin')`.
- **Response:** `200`, `data: null`, or `404` if not found.
- **Caution:** does not cascade-delete the hospital's admin/staff/patient users — they would be left with a `hospitalId` pointing at a deleted hospital.
